# SeumInput

Задержка ввода и мыши с высокой частотой опроса для **SEUM: Speedrunners from Hell**.

Работает через Harmony-патчи поверх оригинальной `Assembly-CSharp.dll`.

## Проблема мышей на 4–8 кГц

`OnGUI` в Unity вызывается **один раз на каждое событие ввода**, а не раз в кадр. В покое
это два вызова (Layout + Repaint), а при движении мыши к ним добавляется по вызову на
каждое мышиное событие. Чем выше частота опроса и резче движение — тем больше вызовов.

Само по себе это было бы терпимо, если бы код отрисовки на не-Repaint событиях ничего не
делал. Но в `Hud.drawScores` часть работы выполняется вне защиты:

```csharp
if (Event.current.type == EventType.Repaint) { ...шапка... }   // под защитой
...
for (i...15)
    if (LeaderboardsBackend.isScoreCurrentUser(leaderboard.scores[i]))   // НЕ под защитой
...
drawScoreLine(score2, m, LeaderboardsBackend.isScoreCurrentUser(score2), formatAsDistance);
//                       ^ вычисляется как аргумент, до Repaint-проверки внутри drawScoreLine
```

То есть на каждое событие, включая мышиные, выполнялось ~40 обращений к Steam за id игрока
(это чинит `CacheSteamUserId` в [SeumPerf](../SeumPerf/README.md) — измерено 3,09 мс за кадр).
Здесь же убирается причина умножения: сами лишние события.

### `SkipMouseMoveEvents` (выключено по умолчанию — по результатам замера)

Префикс на `OnGUI` игровых классов, отбрасывающий `EventType.MouseMove`.

Почему это безопасно — по всему коду игры обращения к типам событий выглядят так:

```
233  EventType.Repaint
223  EventType.MouseDown
  1  EventType.MouseUp
  1  EventType.MouseDrag
  0  EventType.MouseMove
```

`MouseMove` не читается нигде. Ховер считается не из события, а из `GameCursor.position`,
который заполняется из `Input.mousePosition` в `Hud.Update`. Перетаскивание не страдает:
при зажатой кнопке Unity шлёт `MouseDrag`, а не `MouseMove` (единственные два места с
`MouseUp`/`MouseDrag` — это слайдеры в `SeumUI` и `LevelSelector`). Клавиатурные события не
трогаются вообще — они нужны `GUI.TextField` в редакторе уровней и вводе имени.

Патчатся только классы, реально достижимые в игре: `Hud`, `MainMenu`, `LevelSelector`,
`LevelEditor`, `IntroSplash`, `DLCIntroOutro`, `EnterName`, `Strip`, `AudioVisualEditor`.
Демо-сцены из ассет-паков не трогаются — выигрыша нет, а площадь риска шире.

### Что показал замер

На тестовой машине (RTX 4070 SUPER, мышь 8 кГц) гистограмма при резких движениях:

```
OnGUI calls/frame 2,0
   Layout    1,0
   Repaint   1,0
MouseMove dropped 0,0/frame
```

Лишних событий **нет вообще** — Unity не шлёт `MouseMove` в OnGUI на этой конфигурации,
и падение 800 → 130 fps при быстрых движениях вызвано не этим. Патч оставлен
выключателем, потому что сама гистограмма — вещь полезная, а на других конфигурациях
поведение может отличаться. Гипотезу проверять надо, а не верить ей.

### Куда уходит время: замер по фазам

Метод-профайлер [SeumPerf](../SeumPerf/README.md) показал, что при просадке кадр занимает
11,12 мс, а `measured (top level)` — 0,53 мс. То есть 95% времени вне управляемого кода,
и `InputManager_Base.Update` там 0,04 мс, значит Rewired тоже ни при чём. Дальше нужен был
разрез кадра на фазы (`ProbeFramePhases`).

Два прогона, одна и та же сцена, одинаково резкие движения мышью:

```
8 кГц, maxQueuedFrames 2, FullScreenWindow      1 кГц, maxQueuedFrames 1, ExclusiveFullScreen
phase           avg ms  worst ms                phase           avg ms  worst ms
  scripts        0,21      0,37                   scripts        0,07      0,42
  render         1,12     17,64                   render         1,10      2,33
  present+pump   7,11     76,70                   present+pump   0,41      1,37
stalls >16ms: 14,8/s                            stalls >16ms: 0,0/s
```

Читается так:

* `scripts` и **средний** `render` в обоих прогонах одинаковые. Ни игровой код, ни нагрузка
  на GPU не изменились;
* весь прирост — в `present+pump`: 0,41 → 7,11 мс в среднем, 1,37 → 76,70 в худшем;
* 14,8 столов в секунду против нуля.

`present+pump` — это present, оконный message pump и ожидание. Мышиные сообщения выгребает
именно pump, и при 8 кГц их 8000 в секунду. При 7,11 мс на кадре и ~118 fps это ~840 мс из
каждой секунды, то есть около **100 мкс на одно сообщение мыши** — Unity 2018 обрабатывает
каждое WM_INPUT непозволительно дорого.

Заодно снят подозрение с `MaxQueuedFrames = 1`: при этом значении CPU блокируется в Present,
ожидая GPU, и такое ожидание попало бы в тот же бакет. Но во втором прогоне оно стоит 1, а
`present+pump` при этом 0,41 мс — значит эта настройка ни при чём.

Оговорка о чистоте эксперимента: между прогонами менялись три вещи (частота опроса,
`maxQueuedFrames` и оконный режим), а не одна. Вывод держится на том, что `scripts` и средний
`render` не сдвинулись, а `present+pump` вырос в 17 раз.

### Что с этим можно сделать

Из управляемого плагина — **ничего**. Сообщения разгребает нативный player loop Unity,
до него Harmony не дотягивается. Практический вывод: на этом движке 8 кГц непригодны,
1 кГц полностью чист. Стоит проверить 2 и 4 кГц — возможно, порог выше 1 кГц.

Теоретически проблему решает буферизованный raw input (`GetRawInputBuffer` вместо одного
сообщения на пакет) со своим окном и подменой источника дельты в `handleMouseLook`. Это
большая и хрупкая работа со своим оконным сообщением и борьбой с захватом курсора Unity,
а цена ошибки — сломанное прицеливание в спидран-игре. Оценка честная: высокая трудоёмкость,
средние шансы, высокий риск.

Ещё стоит проверить оверлей Steam — он хукает ввод и может быть усилителем.

## Задержка ввода

| Настройка | Что делает |
|---|---|
| `MaxQueuedFrames` (по умолчанию 1) | `QualitySettings.maxQueuedFrames` — на сколько кадров CPU может убежать вперёд GPU. **Игра не выставляет его нигде**, то есть работает на движковом дефолте 2. Значение 1 убирает кадр очереди рендера; на пропускную способность это влияет только когда упираешься в GPU, а эта игра упирается в CPU. `-1` — не трогать. Переприменяется раз в 60 кадров, потому что игра сбрасывает пресет качества при заходе в настройки. |
| `FullScreenMode` (по умолчанию `Unchanged`) | Exclusive fullscreen обычно выводит кадр с меньшей задержкой, чем borderless-окно. Применяется один раз при старте и при смене самой настройки — не постоянно, чтобы игровые настройки экрана оставались главными. |

Что уже в порядке и трогать не нужно: поворот камеры применяется прямо в `Update` через
`transform.Rotate`, своего сглаживания у игры нет, `LateUpdate` только копирует поворот на вид.

Что упирается в геймплей и потому не трогается: движение применяется в
`CharacterMotor.performFixedUpdate`, то есть до одного шага физики задержки. Менять
`fixedDeltaTime` в спидран-игре нельзя.

## Диагностика

### Оверлей (`Overlay`, клавиша `OverlayKey`, по умолчанию **F11**)

```
SeumInput
OnGUI calls/frame  24.6
   Repaint           2.0
   Layout            2.0
   MouseMove        20.6
   MouseDown         0.0
MouseMove dropped 20.6/frame
maxQueuedFrames 1   FullScreenWindow
Rewired before game input: 100%  (18422 frames)
```

Строка `OnGUI calls/frame` — и есть прямое измерение проблемы: в покое там должно быть
около 2, и каждое событие сверх этого — ещё один полный проход по коду отрисовки HUD.
Считаются вызовы `OnGUI`, а не события, поэтому если одновременно активны два
запатченных класса, каждое событие даст два вызова — так и должно быть.

### `ProbeUpdateOrder` (по умолчанию выключено)

Единственный вопрос, который нельзя решить чтением кода: успевает ли `InputManager` из
Rewired обновить состояние устройств **до** того, как `FPSInputController.Update` прочитает
оси мыши. Это определяется порядком выполнения скриптов, который лежит в настройках проекта,
а не в сборках. Если Rewired идёт вторым — каждый прочитанный поворот мыши устарел на целый
кадр, и это дороже всего остального в этом плагине вместе взятого.

Зонд вешает префиксы на `Rewired.InputManager_Base.Update` и `FPSInputController.Update` и
считает долю кадров, где Rewired отработал первым. Если увидишь не 100% — скажи, будем чинить.

### `LogRewiredReport` (включено по умолчанию)

Пишет в `BepInEx/LogOutput.log` версию Rewired, `usingUnityInput` и все скалярные свойства
`ReInput.configuration`. Читается рефлексией: набор свойств у разных версий Rewired
отличается, и отсутствующее свойство должно давать пропуск в строке лога, а не исключение
при старте.

## Конфигурация

Файл создаётся автоматически при первом запуске плагина:

```
<папка игры>\BepInEx\config\SeumInput.cfg
```

<details>
<summary>Пример конфига (SeumInput.cfg) со всеми параметрами</summary>

```ini
[01 - General]

## Общий выключатель. При false плагин не делает вообще ничего.
Enabled = true

[02 - IMGUI]

## OnGUI вызывается один раз на каждое событие ввода, а не раз в кадр, так
## что мышь с высокой частотой опроса умножает стоимость отрисовки HUD на
## число мышиных событий в кадре. Игра нигде не читает EventType.MouseMove,
## поэтому такие события можно отбрасывать до входа в код отрисовки.
## На замерах (8 кГц мышь, резкие движения) гистограмма и так показывает
## ровно 2.0 вызова OnGUI за кадр — то есть отбрасывать нечего, поэтому
## выключено по умолчанию. Оставлено переключателем, потому что на других
## конфигурациях поведение может отличаться.
SkipMouseMoveEvents = false

[03 - Latency]

## QualitySettings.maxQueuedFrames — на сколько кадров CPU может убежать
## вперёд GPU. Игра нигде его не выставляет и работает на движковом
## дефолте 2. Значение 1 убирает кадр очереди рендера. -1 — не трогать.
# Допустимые значения: -1-4
MaxQueuedFrames = 1

## Exclusive fullscreen обычно выводит кадр с меньшей задержкой, чем
## borderless-окно. Применяется один раз при старте и при смене настройки.
# Допустимые значения: Unchanged, ExclusiveFullScreen, FullScreenWindow, MaximizedWindow, Windowed
FullScreenMode = Unchanged

[04 - Diagnostics]

## Показывать гистограмму вызовов OnGUI за кадр по типам событий.
Overlay = false

## Клавиша переключения оверлея.
OverlayKey = F11

## Проверять, успевает ли Rewired обновить оси мыши до того, как игра их
## прочитает в этом кадре (иначе поворот мыши отстаёт на кадр).
ProbeUpdateOrder = false

## Разбивать кадр на фазы (скрипты / рендер / present+pump) и показывать
## средние и худшие значения — так находится задержка, которая лежит вне
## управляемого кода.
ProbeFramePhases = true

## Кадр длиннее этого значения считается «стоп-кадром» (стрОкой stalls/s
## в оверлее).
StallThresholdMs = 16

## Записать в лог версию Rewired и его конфигурацию при старте.
LogRewiredReport = true

## Логировать каждый применённый патч.
VerboseLogging = false
```

</details>
